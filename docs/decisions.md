# Decision log

Short records of choices that shaped the code, newest last. Each says what was decided, what else was on the table, and why.

## D1. Stack: TypeScript on Node, SQLite via better-sqlite3

- **Chosen:** one language across the API and the React UI; SQLite embedded in the API process.
- **Alternatives:** Postgres (needs a separate service to deploy and run in tests); an ORM such as Prisma or Drizzle.
- **Why:** 10,000 employees and about 60k salary rows fit easily in SQLite. better-sqlite3 is synchronous, so each test opens its own `:memory:` database in microseconds, with no shared state and no flakiness. Plain SQL migrations keep the schema readable in review, and the interesting queries ("latest record as of a date") are clearer in SQL than in ORM DSL.
- **Revisit if:** several app instances need to write concurrently. Then move to Postgres; the SQL is close to portable.

## D2. Salary is an append-only, effective-dated history

- **Chosen:** a `salary_records` table. The current salary is a query (the latest `effective_date <= as_of`), not a column.
- **Alternative:** a `salary` column on `employees`, plus an audit table.
- **Why:** the manager's real questions are about time ("what did we pay in March?"). A column answers only "now" and needs a second table to recover the past. With history as the primary data, "now" is just one as-of date among many. A correction is a new record with reason `correction`; nothing is updated in place.

## D3. Money is integer minor units, with the currency on each record

- **Chosen:** `amount_minor_units INTEGER` plus `currency`, with an FK to a `currencies` table that holds the minor-unit exponent (JPY 0, others 2).
- **Why:** floats lose cents. Putting the currency on the record (not the employee) means a relocation from India to the UK keeps the rupee history intact. The FK enforces "valid ISO-4217 currency" in the database, not only in the API.
- **Trade-off:** the `currencies` list is duplicated in the seed's reference data. A test (`seed-write.test.ts`) fails if the two drift apart.

## D4. Future-dated records are allowed

- **Context:** v1 of the requirements said both "effective date not beyond today" and "a future-dated record does not show as current". Under the first rule, the second can never happen.
- **Chosen:** allow future dates and exclude them from "current". The requirements doc was updated to match.
- **Why:** raises are approved before they take effect. Rejecting them would push the manager back to a spreadsheet for exactly the case the tool should handle. The seed includes about 200 scheduled raises so this path is always exercised.

## D5. Constraints live in the schema as well as the API

- `CHECK` for amount > 0, real calendar dates (`date(x) IS x` rejects `2024-02-30`), and an enumerated `reason`. `UNIQUE (employee_id, effective_date)` blocks two records on one day. `STRICT` tables stop SQLite from storing `100.5` in an integer column.
- **Why:** the API will validate first and return friendly errors. The schema is the backstop that also covers the seed script and any future import.

## D6. Indexes chosen from the queries, and verified by tests

| Query | Index |
| --- | --- |
| History of one employee; latest record as of a date | `UNIQUE (employee_id, effective_date)`. SQLite walks it backwards for `DESC`, so the separate `(employee_id, effective_date DESC)` index from the requirements is redundant and was dropped. |
| Filter or aggregate by country / department | `idx_employees_country`, `idx_employees_department` |
| Name search | `idx_employees_full_name` with `COLLATE NOCASE`, which lets case-insensitive prefix `LIKE 'ada%'` do a range seek |

`schema.test.ts` runs `EXPLAIN QUERY PLAN` and asserts `SEARCH ... USING INDEX` for each one, so a refactor that silently drops to a table scan fails CI.

**Name search:** see D9. Word-prefix search does not use this index.

## D7. Seed data is deterministic and generated by a pure function

- `generateSeedData({ count, seed, asOf })` has no I/O and uses a seeded PRNG (mulberry32), never `Math.random`. The same command always builds the same company, and tests assert on real invariants: histories strictly increase, no pay cuts within a currency, and the current currency matches the employee's country.
- Pay is modelled in USD-equivalent and converted per record with a country pay factor. A raise is therefore the same proportional change in any currency, and a relocation switches currency cleanly.
- The writer replaces all data inside one transaction: a bad row rolls back and leaves the previous data untouched.

## D8. Sorting the employee list by salary

**Question:** "Sort by pay, highest first" means computing every employee's current salary before paginating. The options were a resolved table refreshed on write, a window function, or not offering the sort in v1.

**Measured** on the 10k seed, warm cache, sorted page of 50 at offset 5,000:

| Approach | Time |
| --- | --- |
| Correlated "latest record ≤ as-of" subquery, all employees | ~10 ms |
| Same, filtered to one country | ~1–2 ms |
| `row_number() OVER (PARTITION BY employee_id ORDER BY effective_date DESC)` | ~39 ms |

The correlated subquery is one index seek per employee on `(employee_id, effective_date)`, not a scan. The window function numbers all ~61k records before discarding most of them.

**The real problem is correctness, not speed.** An unfiltered sort ranks `amount_minor_units` across currencies and placed ¥14,608,800 (~$97k) between $146,200 and R$146,000. A cross-currency ranking is meaningless without conversion, which is out of scope (requirements).

**Decision:**
- **The sort has a total order:** `ORDER BY current_salary DESC, employee_id ASC`. Seeded salaries round to the nearest 100, so many people share an amount. Without the tie-breaker SQLite may return ties in any order, and with offset pagination page two can repeat someone from page one and drop someone else. Every sort the API offers ends in `employee_id` for the same reason.
- **`sort=salary` needs one currency, either stated or proven.** An explicit `currency` filter always works. Without one, the API looks at the current-salary currencies of every employee matching the other filters (country, department, search). If they all share one, the sort runs in that currency and the response says which (`resolvedCurrency`). Otherwise it returns 400 and names the currencies present. A country does *not* imply a currency: after a future-dated transfer, the employee's country is already the new one while their current salary is still paid in the old currency until the effective date. That is the case D4 exists to support, so the rule has to hold under future-dated data, not only for the seed. The UI disables the column until a single currency is in play, with an explanation.
- Current salary is computed per request with the correlated as-of query. There is no cache.
- **Measured at the route, not only the query.** The budget in the requirements ("under 300 ms") applies to the HTTP response, JSON included, so `PERFORMANCE.md` reports p95 over real HTTP, including the deepest page. Offset pagination costs more as the offset grows, because SQLite still produces and discards every skipped row. If that ever matters, the fix is keyset pagination (`WHERE (salary, id) < (:lastSalary, :lastId)`). At 10,000 rows the measured deep-page cost is reported rather than assumed.
- **Rejected: a resolved table refreshed on write.** A future-dated raise becomes current at midnight without any write, so the table would silently go stale. Fixing that needs a `next_change_date` and a refresh on read: a cache with its own invalidation bugs, to save ~10 ms.
- **Rejected: a window function.** Slower here and no clearer.

**Revisit if** the list query passes 100 ms p95 (e.g. at 100k+ employees). The fallback is a resolved table keyed by employee, holding `current_record_id` and `next_change_date`, refreshed when a write lands or when today passes `next_change_date`.

## D9. Search matches the start of any word, using a scan

- **Problem:** prefix search on the full name (which can use the NOCASE index) won't find "Priya Patel" when the manager types "pat", and that's the most natural thing to type.
- **Chosen:** match the start of any word in the name, or the start of the email: `full_name LIKE 'pat%' OR full_name LIKE '% pat%' OR email LIKE 'pat%'`. User-typed `%` and `_` are escaped. This cannot use an index, so it scans the 10,000 rows.
- **Measured:** 2.1 ms p50 / 2.2 ms p95 at the route (PERFORMANCE.md). That deviates from the requirements' "search against an indexed column" on purpose: the index would buy about 2 ms and cost the search people actually expect.
- **Alternatives:** an FTS5 virtual table (needs triggers to stay in sync, and offers ranking we don't need); a separate indexed `last_name` column (fixes surnames but not middle names or "Wei Ling").
- **Revisit if:** search p95 passes about 50 ms (around 200k employees). Then use FTS5 with a trigram tokenizer.

## D10. Proration and "today"

**Proration rule.** A month's cost is annual ÷ 12, prorated by **calendar days** (not working days). A salary record applies from its effective date, **inclusive**, until the day before the next record. So a raise effective 15 June pays the old rate for 1–14 June (14 days) and the new rate for 15–30 June (16 days). Each currency is summed exactly and rounded **once**, to the minor unit. Rounding each person first drifts by a cent per person. Calendar days were chosen over working days because working-day rules differ by country and depend on holiday calendars, and this tool estimates cost; it does not run payroll, which is out of scope. **Future-dated records:** asking about the current month counts a raise scheduled later in the month for its days. The answer is a projection of the full month, not cost-to-date, and the response says so with `includesScheduledChanges: true`. **"Today" and "this month"** are dates on the org's calendar, set by `ORG_TIMEZONE` (an IANA zone, validated at startup), not the server's clock. A UTC server is still on 30 November for the first 5½ hours of 1 December in Delhi. During those hours it would show November as "this month" and treat a raise effective 1 December as not yet current. On a $120k salary that's about $330 in one day's prorated pay. Effective dates have no time zone (they're the date in the contract), so the only question is whose calendar decides that a day has started. One org-wide calendar keeps every row in a sum on the same "today"; per-employee zones would put a Tokyo raise and a São Paulo raise on different days within the same total. `/api/meta` reports `timeZone` with `today`, so the UI can show which calendar it is using. Tests: `clock.test.ts` (20:00 UTC on 30 Nov is 1 Dec in Asia/Kolkata), plus mid-month raises, the inclusive boundary, February, and scheduled changes in `analytics.routes.test.ts`.

## D11. The UI: Vite + React, served by the API from the same origin

- **Chosen:** a client-rendered React app (Vite, React Router), built to static files and served by Fastify from the same container as the API. `/` is the app; the API's landing page stays at `/api`; any other non-API GET returns `index.html`, so a reload on `/employees/42` works.
- **Alternatives:** Next.js (the brief says React/Next); a separate static host such as Vercel.
- **Why not Next:** every screen here depends on live per-request data (today's current salaries) that one manager looks at. Server rendering buys nothing for that, and it would add a second Node server, or a second deploy, in front of an API that already exists. **Why not a separate host:** one origin means no CORS, one deploy, one URL in the README, and one cold start instead of two.
- **The as-of date is in the header, never in a footnote.** "Current salary" is only true for a date and a calendar (D10). The app header shows "Salaries as of 24 Nov 2026 · Asia/Kolkata calendar", from `/api/meta`. Every heading or column header above money repeats it, taken from the response that produced those numbers rather than from the browser clock. So a page loaded just before midnight in Delhi labels its numbers with the day they were computed for.
- **The salary column follows D8 on screen.** The list response now carries `salaryCurrencies`, the currencies the matching employees are paid in today, and the column is enabled only when there is exactly one. When it is disabled, a line above the table says why ("paid in 8 currencies… choose a currency under 'Paid in'"), because a greyed-out control with no reason looks like a bug. It costs ~5 ms on the unfiltered list (PERFORMANCE.md), against a second ~285 ms round trip.
- **State lives in the URL.** Search, filters, sort and page are query parameters, so the back button from an employee returns to the same filtered page, and a link can be shared.
- **Money input never goes through a float.** "85,000.50" is parsed as a string into 8500050 minor units, using the currency's exponent (JPY rejects decimals). `0.29 * 100` is 28.999… in floating point.
- **No virtualised list.** The requirements ask for one "anywhere a long list is unavoidable". The longest list in the UI is a 50-row page; an employee's history is a few dozen rows at most; the Ask name lookup is capped at 50 matches. None is unavoidable, so there is nothing to virtualise. A list of all 10,000 would be the case for it, and the server-side pages are why there isn't one.
- **Slow first load.** If a request takes over 3 s the UI says the free server is waking (~17 s, PERFORMANCE.md) instead of showing a bare spinner.
